# F32–F33: rain retention and delivery evidence

Rain snapshots now use transactionally maintained hourly, session and lifetime products. New writer instances initialize once per journal inode/process; read-only callers never run schema/WAL setup. Raw events, counters, provenance and summaries commit together before MQTT ACK. Indexed reads fetch the recent hourly window, at most 100 retained tip events, and bounded anchor edges. A single WAL read transaction prevents a concurrent ingestion commit from mixing different snapshot versions.

The engineering default keeps 30 days of raw rain events online. Explicit maintenance archives bounded batches of 5,000 older events and gaps into verified immutable SQLite files. Each boot's last committed packet remains online. SHA-256 manifests, sequence catalogs, content checks and a transactionally committed archive catalog preserve exact duplicate/conflicting-payload behavior after archival. Missing or corrupt archives prevent a historical packet ACK. Lifetime/hourly products remain online; archival does not turn uncertain recovery into measured hourly rain. Anchors outside the retained raw interval are unavailable, never zero. Archive files have no automatic purge policy. These are rain-journal changes; water history is not pruned.

Existing rain journals need an explicit version-3 upgrade before new ingestion/readers run. New journals start at version 3. The main application database separately adds reviewed revision `0003_delivery_evidence`; revisions 0001 and 0002 are unchanged. Both upgrades preserve existing records and must be tested on a backup first. See [RUNBOOK.md](RUNBOOK.md).

System Health now contains an authenticated delivery evidence console. Administrators can record version-checked, reasoned reconciliation decisions with external-evidence SHA-256 digests. Officers have read access only within current station/area/citywide authority grants; residents see only their own deliveries. The console has no resend or bulk reset action. UNKNOWN and PROCESSING retain their observed transport meaning after a review; operator attestation and app callbacks are separate evidence. Any review prevents future automatic attempts for that delivery; a fallback/contact record leaves the incident flagged for follow-up. Stale edits require explicit refresh and manual review.

The existing supervised notification worker now records durable attempts before sending, bounds notification lifetime (default 300 seconds), retains allowlisted provider message references and reports progress between deliveries. Four injected interruption boundaries demonstrate that PROCESSING is never automatically reclaimed or resent. Queue-age and ambiguity alarms remain in workflow diagnostics. No real worker or provider was activated during this implementation.

Resident mobile's **Alerts → Push delivery evidence** separates queued, provider accepted, app received, opened and explicitly acknowledged stages. Optional callback collection is off by default and versioned. Capabilities are scoped to a delivery/attempt, expire after seven days by default, survive same-installation token rotation and normal API-session expiry, and are invalidated by consent changes, device withdrawal or account deactivation. Only hashes are stored server-side. Explicit acknowledgement requires the resident's current authenticated session and displayed evidence version.

Received/open callbacks use a separate encrypted local namespace without reading resident API credentials in a background isolate. At most 200 records persist for seven days with original client timestamps; bounded drains run on callbacks, foreground resume and manual evidence refresh. The UI reports unconfirmed queued callbacks and discarded/expired capabilities. Callback evidence is app-reported; no missing stage is inferred from another stage. Background callbacks depend on OS delivery behavior and may be absent even when a notification was displayed. Firebase distinguishes provider acceptance from device/app delivery; see [delivery evidence](https://firebase.google.com/docs/cloud-messaging/understand-delivery) and [Flutter callback behavior](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages).
