# F24–F25: response resources and offline resident reading

Implemented October 22, 2026. Software implementation does not establish shelter activation, road passability, flood-safe access or real operational dispatch. No real shelter, authority, phone number, road closure or preparedness instruction was invented or seeded. Live source inventory remains empty until an authorized maintainer supplies and reviews it. [Verification results](RESULTS.md) separate automated evidence from installed-device and operational acceptance.

## Authority-maintained resource registry

The staff web **Shelters & Access** page manages three resource kinds: shelters, reported road restrictions and preparedness/contact references. Each record has a stable identifier, issuer and verified area identifiers, Actual/Exercise namespace, source evidence, content, version, verification state and expiry. Actual records require an active public authority with verified geographic areas and an explicit staff grant covering every affected area. App-operator grants support Exercise records only. Resident mobile is read-only and cannot read exercise inventory or unpublished drafts.

Shelters carry address/entrance, coordinates, inactive/active/full state, recorded activation time, nullable capacity/occupancy, capacity-observation time, nullable wheelchair access, services, access constraints, instructions and contacts with stated hours. Unknown capacity/accessibility remains unknown. Capacity is a recent report for at most 30 minutes; it does not reserve space. A reported full shelter stays full when that capacity observation grows old. Numeric capacity/occupancy requires its original observation time. Active/full state requires an activation time.

Road reports carry closed/restricted/reopened status, bounded line geometry, source, access constraints, instructions and contacts. The registry is a **partial source inventory**, not a complete road network or proof that unlisted roads are open. No road-closure provider integration is claimed. Preparedness references contain source-reviewed text and contacts; there is no fabricated fallback telephone or default emergency instruction.

Saving content creates an unverified revision. A separate verification action reviews the persisted version and sets an expiry between one minute and seven days. Activation and capacity observations cannot claim a future measurement. A new unverified draft is hidden from residents. Editing a previously published record leaves it visible as unverified, with its instructions/contacts withheld until reverified. Withdrawal, expiry and unavailable issuing authority remain explicit. Disabling an issuer or area removes the record's current verified trust on the next API read. Previously verified cached text is historical and cannot certify current activation or passability.

All content and verification writes require `expected_version` and reason. A conditional UPDATE prevents two editors from silently overwriting each other. HTTP 409 includes the refreshed current record; the web discards rejected inputs and requires explicit refresh/manual review. No stale mutation is automatically replayed. Verification is disabled while local content edits remain unsaved. Immutable revision snapshots record actor, version, reason and original source/content; general mutation audit records the change. ORM append-only guards do not replace database ownership and privilege controls.

### API

- `GET /api/response-resources?kind=shelter|road|preparedness&mode=Actual|Exercise&area_id=...&include_drafts=false&limit=50&offset=0`: authenticated, bounded to 100 rows, exact area membership, total/has-more/source-coverage metadata. Drafts/Exercise are staff-only. Responses are `no-store` for intermediary/browser HTTP caches; the resident app's explicit encrypted reader cache is separate.
- `GET /api/response-resources/maintenance-context`: staff issuer grants and verified area choices, bounded to 100 grants/200 areas.
- `POST /api/response-resources`: authorized create/edit with expected version, reason and typed resource content; new IDs use version 0.
- `POST /api/response-resources/{id}/review`: separate verify/withdraw with expected version and reason; verification requires expiry.
- `GET /api/response-resources/{id}/revisions?limit=50&offset=0`: bounded staff revision review.

The mobile fetches at most 100 records per kind and displays any truncation explicitly. Issuer and area administration remain in the existing governance workflow. Staff cannot replace a record's issuer, kind or namespace to evade ownership checks.

## Maps and usable text fallback

The hardcoded UCU Gym destination was removed. The map and the independent scrollable resource list use the registry. Original source, issuer, verification/expiry, activation, capacity time, services, accessibility and access constraints are visible with contacts. Inactive, full, unverified, expired and cached destinations cannot initiate directions. The base map's initial city-center coordinate is a camera default, not a shelter or user location.

Reported road restrictions are overlaid separately from Google walking directions. Generic route estimates and provider warnings never establish flood safety and do not incorporate these reported closures. GPS is requested only after a deliberate action; GPS denial, unavailable WebView, quota/provider failure and route failure leave the text inventory and contacts available. External directions carry the same limitation. No distance/duration of zero is substituted when a route estimate is unknown.

## Encrypted last-known reader cache

The app uses the existing `flutter_secure_storage` provider for cache and identity data, with no plaintext storage fallback. The installed 10.3.1 package documents Keychain storage on Apple platforms and default RSA OAEP/AES-GCM ciphers on Android. Android backup is already disabled in the application manifest. This implementation was inspected and adapter behavior was tested; actual at-rest encryption, device-key recovery, OS backup/restore and cold airplane-mode acceptance still require installed-device testing. Web secure storage has a browser origin/XSS/device trust boundary and is not equivalent to native Keystore/Keychain protection. Release deployment must use HTTPS and appropriate browser security controls.

Cache keys are scoped to the API base URL digest and resident owner. Identity contains the resident profile and a digest bound to the existing secure session token; it is **not offline server authorization**. A transport/5xx failure can restore that matching resident into an explicitly read-only reader. Staff profiles, mismatched token/origin, expired entries and detected clock rollback cannot restore it. Known 401/403 failures never fall back to cached responses; 401 clears reader identity/data. A different login removes the prior reader bundle. Local reader exit clears local session/cache access; without a server connection it cannot claim to revoke server sessions or push registrations. SOS references are separately preserved to prevent duplicates.

Monitoring, official notices, community episodes/detail/history, received SOS history and response resources have an allowlisted GET cache. Raw server timestamps and values are preserved; cache-save time is additional metadata. Monitoring entries last at most 24 hours. Other reader entries and identity last at most seven days, with 24 entries, 128 KiB per entry and 512 KiB per owner bundle. Old entries are evicted and expired data purged on access/write; an app that is not running cannot physically purge its encrypted storage on a wall-clock deadline. Saved reader offsets and last episode are bounded and merged serially. Storage failure is surfaced instead of silently falling back to plaintext.

A cold offline reader displays **LAST KNOWN / NOT LIVE**, original measurement age and source dates. Cached water/rain connectivity cannot become LIVE. Cached official notices may be missing later updates/cancellations and retain their original effective/expiry times. Cache failures affect each resource feed independently. A failed feed does not revoke a currently verified session or block an explicit SOS POST to an available service; any attempted send still needs a real server receipt. Only cached-identity restoration enters the read-only offline reader. Nothing in cache proves current hazard, response status, shelter activation or road access. A deliberate **Verify connection & refresh** validates the session with the server before enabling writes; it never auto-sends a saved SOS. Push registration changes are paused while the resident session is unverified; this does not claim that the OS has revoked an existing push registration.

## Durable practice SOS outbox

The original secure draft store now persists an explicit outbox envelope alongside the exact original request payload/reference. The envelope contains source installation, queued time, last attempt, state and one last confirmed receipt. Metadata never goes to the SOS creation API. It has a 16 KiB budget per owner. Pending/unconfirmed references do not automatically expire: deleting an uncertain request could encourage a duplicate. Residents can inspect the original location/message, reference, capture time and attempt time.

| State | Meaning and allowed action |
| --- | --- |
| Queued | Saved locally before any attempted transmission; explicitly labeled NOT SENT/NOT RECEIVED. After connection verification the resident can send the saved exact payload, or discard an unsent draft. |
| Unknown | Transmission may have reached the server but receipt is unconfirmed. Check exact-payload receipt or explicitly retry the same payload/reference. No discard, new reference or automatic resend. An unsuccessful later retry cannot erase the uncertainty of an earlier attempt. |
| Rejected | A first attempted request was explicitly rejected. Details remain inspectable; explicitly discard before correcting. This label is not used to erase an earlier unknown attempt. |
| Conflict | Reference/payload or installation mismatch. No automatic retry, replacement or overwrite; manual review is required. |
| Received | A positive server response or exact-payload receipt match. One durable receipt remains across restart; receipt/acknowledgement does not claim dispatch. Current lifecycle status can still be unavailable. |

`POST /api/sos/receipt` is a resident owner-only, **read-only** lookup using the original `SosCreate` normalization/hash. It returns `unseen`, `conflict`, or `received` with the current sanitized record. It cannot create an SOS. An absent record does not prove an in-flight original request will never commit, so unseen does not downgrade unknown to queued. A matching UUID in ordinary history is insufficient proof of payload receipt. Later accepted GPS updates do not change the original creation hash. Known conflicts require manual review and never overwrite newer server data.

Legacy flat drafts are conservatively restored as unknown. Old drafts lack an origin marker; review the original installation before manually retrying them. New envelopes bind the source server and block cross-installation replay. The outbox does not auto-send on startup, login, network recovery or reader verification. A stale first-send GPS capture may be rejected; the resident must explicitly review/discard a definitely unsent/rejected draft and capture a new fix or choose manual location. Practice remains segregated from operational response, which remains disabled under F23.
