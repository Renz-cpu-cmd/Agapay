# F34–F35: reviewed water-depth models and one published forecast

**F34 remains a field-data and scientific-validation prerequisite.** This change implements preparation, baseline evaluation, a transparent candidate adapter, model cards and independent approval. It does not create real paired observations, establish a physical datum, train a real operational model or claim field accuracy. Existing H5/scaler placeholders are never loaded. The installed registry starts empty, and operational screens show unavailable/untrained until the reviewed prerequisites are met.

**F35 uses one persisted product across web and resident mobile.** The existing authenticated `GET /api/predictions/{station_id}` now reads a published station product. A bounded publisher evaluates an independently approved adapter once per input/binding fingerprint and commits an immutable forecast ID. Viewer requests never fit a model, modify basin parameters or generate a private forecast. A record contains site, local depth target in cm, datum, input cutoff, registry-owned device identity/version, model-card ID, installation hash, deployment version, generation time, expiry and exact target timestamps. Staff/resident reads of the same ID share the stored values. Per-request check/read times can differ; generation/cutoff/expiry never change because someone opens the record.

Operational dashboard/station cards and resident home/detail cards use that product. Tapping the forecast ID opens the original record on either client. Historical, expired or withdrawn records remain explicitly separate from current forecasts; opening them never extends validity or implies a current hazard. Model revocation, commissioning/lifecycle/configuration changes and source identity changes prevent the old product from returning as an available operational forecast. No forecast changes measured hazard tiers or issues an official action notice.

Private rainfall/basin experiments remain in the staff ML Configuration workspace with persistent experiment labeling and browser/account-local settings. Residents cannot read or mutate that endpoint. Ordinary rain panels on both platforms use the new observation-only rain activity endpoint and perform no basin inference. A failed or unavailable forecast never causes entry into the experiment. Production can serve an approved water-depth product independently of development-only hybrid settings; otherwise it returns a clear unavailable response with null predictions.

ML Evaluation now reads `/api/forecast-registry`, which reports registered water-depth cards, approval versions, baseline/error comparisons and the experimental artifact selected by backend settings. The page no longer hardcodes a filesystem directory/version or training years. Experimental evaluation and inference resolve the same configured artifact/dataset, verify their provenance hashes and identify rainfall evaluation separately from water-depth accuracy. Missing experimental files do not become operational water-depth evidence.

Apply reviewed main database revision **0004_forecast_registry** offline; older migration snapshots remain unchanged. [RUNBOOK.md](RUNBOOK.md) covers data acquisition requirements, the offline candidate workflow, independent review, station binding, worker activation and rollback by disabling the binding. [RESULTS.md](RESULTS.md) records observed verification and remaining field/deployment acceptance.

The later [F36–F37 safeguards](../F36-F37/README.md) extend approval with separate calibration events, reviewed decision tradeoffs, event-based intervals, subgroup checks and out-of-domain rejection. Passing the original average-error gate alone is no longer sufficient.

## Training and evaluation boundary

The first supported candidate predicts **local sensor depth above an explicitly commissioned datum**, in **cm**, at **30/60/90 minutes after the latest measured input**. It does not predict inundation area, safe routes, community safety or authorized evacuation. It uses two causal water features: current valid depth and a robust rate from minute medians/pairwise slopes over the preceding 30 minutes. The same feature implementation runs offline and at inference. Rainfall is collected with explicit native interval and availability metadata when available, but is **not an input to this first water-only adapter**. ERA5 archived/future rainfall cannot silently become an online feature. Adding a rain-dependent adapter requires a new feature contract, availability validation and independent evaluation.

The preparation tool accepts one site/datum/calibration/source at a time. Observations and rainfall intervals retain their actual availability times; unavailable/invalid water values are not zero-filled. It requires exact observed targets, never interpolation. Entire events are assigned to train or withheld test, with a 90-minute cutoff embargo. Candidate origins are at least five minutes apart, one-hour input windows are bounded to 3,600 samples, and publication uses the same provisional input coverage/quality gates. The fixed regularized linear depth-delta candidate is fitted only on training events; no tuning uses the withheld events. These are engineering defaults, not evidence of field suitability.

Reports compare the candidate against **persistence** and **measured-time rate extrapolation** at each horizon, including count, MAE, RMSE, bias and maximum absolute error. An approval gate requires a physical-field source declaration, three distinct training and three withheld events, at least 30 withheld origins, finite supported-range output and lower MAE than both references at every horizon. Passing those minimums does not establish disaster-response suitability: an independent reviewer must inspect original collection/calibration/licence records, event grouping, missingness, severe-event failures, transfer limits and allowed use. Source declarations and evidence digests are not hardware attestation or proof that a person performed a valid review.

The [model-card framework](https://arxiv.org/abs/1810.03993) motivates explicit intended use and evaluation limitations. Temporal ordering and an embargo address future-information leakage; see [scikit-learn's time-series split guidance](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html). This implementation additionally withholds whole events; it does not use random row splitting or claim that adjacent samples are independent events.

## Contracts

Hybrid requests/responses, rain-only responses, model cards and published forecast records have explicit Pydantic schemas. The exporter reads the actual FastAPI OpenAPI document and writes [forecasting.openapi.json](../../contracts/forecasting.openapi.json), generated TypeScript/Dart publication-field manifests and a shared **synthetic** valid/invalid corpus. Backend, TypeScript and Dart validate the same zero-valued product and reject missing identity/provenance, wrong cutoffs, mismatched cards and malformed configuration hashes. `python -m app.export_prediction_contracts --check` detects drift. Fingerprints normalize line endings for Windows portability.

The immutable record endpoint returns the original product plus `read_at` and `current`. Latest operational reads use the current server check time to calculate remaining lifetime, retain the original expiry, and remove numeric values on expiration. Default product lifetime remains 60 seconds, capped by the input's 120-second age limit. These provisional freshness settings are not calibrated prediction confidence or a delivery SLA.
