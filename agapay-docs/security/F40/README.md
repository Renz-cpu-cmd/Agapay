# F40 — privacy, recovery and service ownership

Implementation date: 2026-10-23. **Development controls and review package; organizational/legal approval and production recovery acceptance remain pending.** No real organization, DPO, issuing authority, support roster or service agreement was invented. No live account, incident, provider, backup or database was changed during validation.

## Implemented behavior

- An additive `0005_privacy_recovery` migration adds versioned privacy cases/holds, append-only privacy evidence and a recovery quarantine fence. Prior migrations remain unchanged. Serving verifies schema; it does not migrate or purge data.
- Signed-in owners can request access, correction or erasure review after current-password verification. Open requests of the same kind are deduplicated under the account lock. Requests have an internal 15-day review target, **not a statutory deadline or promise of emergency response**.
- A bounded owner export returns account, preferences/subscriptions and pages of the owner's SOS records. It excludes password hashes, API/MFA secrets and provider tokens. It explicitly is not an automatic complete data-subject access response: retained audit/delivery evidence and third-party information require review through the case. Mobile displays an ephemeral selectable copy; web downloads a deliberate personal-data file. Copies the user retains need separate protection.
- Administrators review cases, evidence hashes and justified, expiring holds. Officers/residents cannot administer them. Version conflicts return 409 and require explicit refresh/manual review. Hold/account locks and SOS write guards prevent a new SOS from slipping through a reviewed account erasure. Recovery rechecks an account after its lock before queuing identity mail.
- Account-bound identity mail rechecks account activation, contact and version under the account lock and holds it through the send outcome. Erasure either precedes that check or waits for the recorded send boundary; a committed SENDING claim remains non-replayable after a crash. SMTP timeouts bound individual network operations but a slow provider can delay account changes, so monitor the worker and keep maintenance offline. Earlier provider disclosures still require external review.
- Explicit application erasure requires an IN_REVIEW resident case, current administrator password, current case/account versions, no open SOS and no active hold. It pseudonymizes the account, changes its password hash, deactivates access, revokes sessions/push, removes current preferences/subscriptions and identity actions, and redacts personal fields in closed SOS and related free-text audit/activity evidence. The case moves to **AWAITING_EXTERNAL**, not completed. Staff records require separate review.
- Historical incident IDs, exact-payload idempotency digests, lifecycle/action/timestamps and pseudonymous delivery/case references remain. They must not be described as fully anonymous. Backup/external-copy review and justified residual record retention are explicit completion gates. Completion records an administrator's actual evidence attestation; a hash alone proves neither deletion nor legal approval.
- A narrow, recorded privacy exception permits SQL redaction of account/SOS audit personal fields while preserving event identities/action/time. Ordinary audit edits/deletes remain forbidden. Privacy events themselves contain controlled identifiers, reason codes, counts and evidence hashes, not deleted personal content. This exception requires organizational review before public use.
- `python -m app.privacy_retention` is a bounded **dry run by default**. Explicit application is an offline maintenance action with writers stopped; it is not silently scheduled or enabled. Holds and open incidents are excluded; held rows and ambiguous identity mail do not block later eligible rows in a batch. Counts are bounded observations, not total inventory counts. See the [retention matrix](DATA-INVENTORY.md).
- Privileged access review captures staff role/activity/version/MFA registration and authority scope without contact details. An administrator verifies the unchanged snapshot with current password and evidence hash; changed inventories require manual refresh. MFA registration alone is not proof of recovery readiness or least privilege.
- Encrypted recovery packages use streaming AES-256-GCM, member checksums, schema/row fingerprints and an optional consistent SQLite rain-journal copy. SQLite and reviewed libpq PostgreSQL service inputs are supported. Restore only targets a new directory/empty database and authenticates the package before extraction. No service is started.
- Restored databases are quarantined. Old sessions/push tokens are revoked; pending/retryable notifications are suppressed; processing deliveries become UNKNOWN; existing UNKNOWN/SENT history is retained; identity mail/actions are disabled. API startup, production worker preflight and notification/mail processing refuse the fence. Restoring data never blindly replays historical alerts.
- Production startup/preflight requires a current external organizational policy/service attestation matching the actual policy hash and exercise evidence. Readiness degrades when the attestation expires or data is quarantined. Development continues to display its unapproved state.

## Locations and providers

The mobile SOS map now requires a deliberate action before it receives coordinates. It can be hidden again, and marker text does not include the resident's address/narrative. Text location/contact information remains usable without a map. Web SOS maps already require an explicit map action. A coordinate already disclosed to a provider cannot be withdrawn by hiding the widget; external retention and the provider agreement require organizational review.

No SMTP, Firebase, APNs, Google Maps, managed database or storage account was provisioned. No external message was sent. An organization-attested record is not a compliance certificate.

## Deployment sequence

1. Review [data inventory and retention](DATA-INVENTORY.md), [PIA and ownership decisions](PIA-AND-OWNERSHIP.md), and [incident/recovery runbook](OPERATIONS-RUNBOOK.md).
2. Take a verified encrypted backup of the actual existing stores; rehearse migration/restore on copies. Apply ordered migration offline with the existing migration command. Do not reset or reseed the database.
3. Run access and retention exercises on reviewed data copies. Record real evidence hashes, approved notice/version and accountable contacts in a protected copy of `service-governance.example.json`. The example is intentionally unapproved. Set `AGAPAY_SERVICE_GOVERNANCE_PATH` to that reviewed file; its values must match the actual deployment.
4. Establish managed encrypted backups/PITR and key escrow. Measure actual recovery point, full service restoration time, privacy-withdrawal reconciliation and no-replay behavior in the intended PostgreSQL/storage/provider deployment. The local synthetic SQLite drill does not establish production RPO/RTO.
5. Activate public use only after organizational/privacy/legal review, operator coverage, release/device gates and actual restore/incident drills pass. No automated tool fills these approvals on the organization's behalf.

The [NPC PIA guidance](https://privacy.gov.ph/5-pillars-of-compliance-2/) describes assessing data flows, purposes, recipients, retention and risks throughout a system's lifecycle. The project-specific review below follows that approach; it is not a legal compliance determination.
