# Personal-data inventory and retention contract

Status: development policy v1, unapproved for public use. The responsible organization must establish lawful purposes/bases, processor locations/agreements, access rights and retention justification. Registration is not assumed to be blanket consent for unrelated processing. Free-text fields may contain additional personal information; operators must not put unnecessary personal details into reasons, notices, logs or evidence references.

| Store / data | Purpose and authorized recipients | Retention / disposal behavior |
|---|---|---|
| `users`: name/email/phone/self-reported locality, hashed password, verification/version | Owner account; admin account management; authorized incident/contact workflows | Account lifecycle/manual review; explicit resident application erasure pseudonymizes and disables. Stable user ID remains for integrity. Staff accountability records require separate review. |
| `auth_sessions`: hashed bearer identity, audience, expiry/MFA time | Session authorization; owner device management; privileged security operations | Existing expiry pruning; deliberate logout/erasure/recovery revokes. Raw bearer tokens are not stored here. |
| `identity_actions`, `identity_mail`: email/profile invitation, hashed action token, encrypted recovery/verification body, expiry and send state | Verified recovery/invitation; configured SMTP operator/provider | Offline retention removes actions expired over 14 days and dependent mail; UNKNOWN/SENDING mail is held for operator reconciliation. Erasure removes the resident's action/mail records. SMTP/provider copies are external fulfilment items. |
| MFA encrypted seed/recovery-code hashes | Privileged MFA and recoverability | Active identity lifecycle; protected key escrow separate from database backup; erasure removes any resident credentials. Staff lifecycle needs controlled recovery/access review. |
| `notification_devices`: provider token, installation ID, authorization/session hash/revision | Opted-in resident push through configured FCM/APNs providers | Deliberate revocation clears tokens; offline retention also clears disabled legacy tokens older than 30 days. Delivery/device IDs remain pseudonymous references. No device receipt is inferred from FCM acceptance. |
| Delivery attempts/receipts/reviews, consent, event/device/account links | Explain queued/provider/app/open/acknowledged stages; authorized owner/staff console | Evidence review target 365 days; actual archival/purge requires reviewed integrity/hold policy. Uncertain delivery never reset to pending. No automatic bulk deletion of delivery evidence is claimed. |
| Area/station subscriptions and account preferences | Explicit targeting, locale, optional receipt collection | Owner changes; resident erasure deletes current records. Free-text barangay is not verified exposure. Mobile local preferences/cache have their own account scope. |
| SOS account snapshot, message/location description and **latest** coordinates/accuracy/capture time | Owner and authorized staff incident/drill handling; map provider only after explicit map action | Open requests retained pending response/review. Closed structured location and location-capable free text removed after 7 days by maintenance; name/contact/locality snapshot removed after 30 days. Holds exclude records. No continuous GPS trail is claimed by this schema. |
| SOS response/audit free-text details and historical actions | Staff accountability; resident-visible recorded response | Location-capable free text is redacted with the closed SOS; event IDs/action/time remain. Staff actor identity and pseudonymous incident reference remain under reviewed accountability retention. |
| General mutation audits: actor label, before/after account/config data, reason | Authorized administrator review/security/accountability | Review target 365 days, not automatic deletion. Controlled resident erasure removes personal account snapshots/actor labels and related SOS narrative evidence, preserving event metadata and recording a privacy event. Other free text requires inventory review. |
| Privacy cases, holds and evidence | Rights fulfilment, justified exceptions, retention/access review | Minimal identifiers/codes/counts/evidence hashes. Review target 365 days; a hold has an explicit expiry within one year and must be justified before renewal. Do not attach IDs, passwords or raw documents to these fields. |
| Auth abuse budgets and operational metrics/logs | Shared abuse control, diagnostics and correlation | Existing bounded counters/metric windows; pseudonymous hashed keys may remain identifying. Deployment log retention must be configured and reviewed; avoid request bodies, exact SOS fixes and credentials in logs. |
| Station/telemetry/rain, forecast artifacts, verified shelters and notices | Observation/response products and public information where explicitly intended | Measurements are separate from personal resident records. Station installation details, issuer/reviewer names and free-text metadata can still identify staff; review permissions and public visibility. Existing rain archival integrity/retention rules remain. |
| Mobile secure storage/cache/SOS drafts/receipt journal | Offline last-known data, original timestamps, exact-payload retry and user preferences | Existing encrypted account-scoped bounded storage; logout clears account-private state. A disconnected device cannot receive immediate revocation/erasure. Device cleanup, cache expiry and resident-held exports belong in fulfilment review. Unsent SOS is never called received. |
| Web session cookie/browser preferences/downloaded own-record pages | Sign-in, local theme/selection, explicit owner export | HttpOnly session and deliberate sign-out; no password/export written to application localStorage by privacy UI. Downloaded files/user clipboard copies are user-controlled and contain personal information. |
| Encrypted DB/rain backups, managed PITR, model/artifact/config references, protected key escrow | Authorized recovery operators; separately controlled hosting/storage processors | Development target: 30-day rolling backup retention. The new tool encrypts and verifies packages; it **does not automatically delete old backups, configure cloud/PITR retention, or destroy escrow keys**. The chosen storage platform must enforce and evidence the schedule. Encryption is not proof of erasure. |

The maintenance command reports bounded counts and whether more passes may be needed. Run repeated passes until no eligible rows remain, then verify protected samples without copying raw data into logs. Holds and uncertain mail require separate review; do not force expiry or resolve incidents merely to pass retention checks.

## Data-subject workflow

1. Owner verifies current password and records a minimal access/correction/erasure case. An unauthenticated/lost-account request uses the organization's verified recovery/contact process; do not demand unnecessary identity documents or paste them into this app.
2. Operator validates identity/scope, checks duplicate/open cases, justified holds, unresolved SOS, recipients and relevant backups. Retain evidence in the protected organizational case system; only its SHA-256 reference enters AGAPAY.
3. Access: paginate owner records, review additional audit/delivery evidence and third-party data, deliver securely, then record actual delivery evidence. Correction: use existing version-checked profile/administrative workflow, record what was corrected or explain the reviewed exception; do not rewrite measurement/incident history silently.
4. Erasure: review the current account/case versions and reason. The explicit resident action disables the account and performs scoped application minimization, preserving necessary pseudonymous referential evidence. It stops at AWAITING_EXTERNAL. No account erasure while an SOS remains unresolved or a justified hold is active.
5. Reconcile external processors, retained accountability records, personal exports/local devices and backup/PITR expiration. Keep a current protected withdrawal/erasure ledger outside older backups. Before activating any restore, reapply post-snapshot withdrawals and justified retention/holds so old personal information is not silently resurrected.
6. Record external evidence and explain any justified residual retention before completing the case. The review target in code is an internal default; the responsible privacy/legal owner determines applicable obligations and deadlines.
