# F26–F27: shared mobile freshness and protected production transport

Implemented October 22, 2026. [Results](RESULTS.md) distinguish software tests, isolated TLS/broker checks and synthetic ESP32 compilation from field deployment. No existing broker was reconfigured, no device was flashed, no NVS/eFuse was changed, and no real credential was displayed or replaced.

## F26: one observation store and one freshness contract

Map no longer owns a polling timer, loading/error state or selected-station copy. It subscribes through the existing AppController/MonitoringController, uses the same selected station as home/detail/forecasts and invokes only the controller's explicit refresh action. The sole monitor polls every five seconds and notifies age changes every second, even during a hanging/failed network request. In-flight requests are bounded by the API timeout and owner-generation checks; an old account's late response cannot replace the current account's snapshot. Concurrent refresh attempts are coalesced.

`StationFreshnessView` is immutable and evaluates depth, independent rainfall and device heartbeat at one observation instant. Each channel exposes original measurement time, age, value (nullable), quality, source, state and freshness. Snapshot/history lists and nested configuration/rainfall/lifecycle values are also immutable. Missing, invalid, retained/stale, unverified and current values remain distinct; numerical zero stays a real value. A recent heartbeat does not renew an old depth or an absent rain interval. Time moving backward beyond the clock-skew budget cannot make a measurement current.

Depth is current only with an unexpired heartbeat, valid quality, current measurement age, trusted physical depth provenance, operational stream and no review hold. An untrusted retained depth is explicitly labeled unverified even if a later heartbeat has trusted provenance. Historical active hazards remain unresolved when observation freshness expires; the view does not infer recovery. Home, map, sensor detail and forecast context share the same source/quality/freshness presentation. Forecast station selection now follows the shared selection and invalidates old forecast responses; forecast validity remains a separate model contract, not a substitute for current observations.

## F27: environment and TLS boundaries

| Surface | Development | Production |
| --- | --- | --- |
| ESP32 | Explicit `AGAPAY_LOCAL_DEVELOPMENT=1`; existing local demo transport | Separate `esp32-production` profile, `AGAPAY_RELEASE_BUILD=1`, development flag 0, TLS listener 8883 |
| Firmware configuration | Existing ignored `secrets.h` and prototype fallback remain usable for local work | Requires separate protected `release_secrets.h`, `transport_secrets.h`, provisioned `ingest_secrets.h` and reviewed `station_config.h`; never falls back to demo credentials/geometry |
| Device broker identity | Existing development setup | Unique broker username equal to commissioned station ID, independent strong broker password and station ingestion token |
| Certificate verification | Local transport explicitly labeled development | `WiFiClientSecure` with reviewed PEM CA, hostname validation through the installed ESP32 TLS stack, five-second handshake budget; no `setInsecure` fallback |
| Device clock | Existing SNTP | MQTT connection withheld until usable UTC exists; local sensing and local fail-safe outputs remain independent |
| Local exercise override | Explicit bench profile/Serial commands | Bench build flag rejected and runtime distance-demo override disabled; bounded operator output self-test remains a separate diagnostic |
| Backend MQTT | Authenticated local development can use plaintext | TLS mandatory when enabled; plaintext demo ports, missing broker identity, development client ID and unpaired mTLS files rejected |
| Backend TLS trust | Explicit opt-in for local work | System roots or configured CA file, `CERT_REQUIRED`, hostname verification and TLS 1.2 minimum; bad/missing CA files fail without plaintext fallback |
| Public API/mobile | Loopback/emulator defaults in debug | Backend requires reviewed public HTTPS API/web origins; mobile release rejects missing/insecure/local/credential-bearing/path/query origins on every platform, including web |
| Staff web startup | Existing local Next commands | `npm run start:production` validates explicit production environment and reviewed web origin; upstream must be verified HTTPS or deliberate same-host loopback HTTP |

Production example files are templates, not deployed configuration. `deploy/https-api.nginx.conf.example` terminates TLS 1.2/1.3, bounds bodies, supplies HSTS/nosniff and forwards only to loopback FastAPI. Keep the internal API and development broker listeners off exposed interfaces with real firewall/service controls. The example does not create DNS, certificates or a trusted proxy identity. Existing F20 signed client-IP/proxy and staff MFA requirements still apply. Backend optional client-certificate/key support is available; the device profile currently uses server-authenticated TLS plus per-device broker passwords, not device mTLS.

## Provisioning, rotation and revocation

1. Commission the actual physical station through authorized administration. Preserve device ID, installation revision, reviewed geometry and applied configuration hash. Render the sensor header through the existing `render_station_config.py` workflow; this does not establish physical calibration by itself. Development prototypes cannot substitute for reviewed field geometry.
2. Create a unique broker account named exactly as the station ID and a separate station ingestion token. Use an operator prompt or protected secret system for broker passwords; do not put real passwords in shell arguments, CI logs, source control or shared fleet credentials. Install private headers from protected per-device mounts. `.gitignore` reduces accidental commits and is not a filesystem access control. Production binaries containing credentials must be protected too. Review secure boot, signed delivery, flash encryption and physical custody before field activation; no hardware trust feature was enabled by these changes.
3. Export reviewed active physical identities and stage an ACL with `python -m app.broker_acl --input <reviewed-identities.json> --output <new-staged-acl>`. It refuses existing outputs, invalid/duplicate IDs and active simulator identities. The resulting per-device entries allow only its water/rain publishes and its own rain acknowledgements. Backend-ingest can read operational measurements and publish acknowledgements; it cannot publish operational telemetry. Exercise identities require a separate broker/environment. The renderer checks identifiers and roles, not the truth of commissioning evidence.
4. Review the staged ACL and password store before installing them with broker-service-only access. First-time password-store creation must target a new staged file; never use a destructive create option against an existing live store. The production broker template uses the staged explicit ACL rather than the permissive development pattern file, disables anonymous/retained operational publication and bounds message/queue sizes. Expose only the reviewed TLS listener; firewall plaintext development ports.
5. Coordinate rotation of the station's API token, broker secret and protected device configuration. Existing station credential administration provides audited ingestion-token rotation/revocation; broker credentials are an independent control. Verify the replacement connection and station-scoped ingestion during a supervised window. No automatic fleet-wide rotation or remote flash is claimed.
6. For revocation, revoke the ingestion identity/token, remove or disable broker permissions/account and terminate existing authenticated connections. Reloading a password file alone must not be treated as disconnection. Use the deployment's supported per-client control or a supervised listener restart, with the availability impact reviewed. The isolated test changes the password and restarts its own listener, then proves the old password is rejected. It never restarts a real broker.
7. Maintain CA/certificate expiry and root-rotation records. Obtain anchors through a reviewed channel, verify broker DNS against certificate SAN and stage trust changes before expiry. Invalid CA, wrong host, expired certificate and unsynchronized time must stop publication while local sensing continues. Record the build artifact hash, protected secret source, trust anchor, operator and validation evidence separately from sensor calibration.

## Web security headers and Maps compatibility

A request proxy creates a cryptographically random nonce per HTML request, overwrites client-supplied nonce/CSP headers and applies the same policy to Next rendering and the response. Root layout is dynamic, and the before-paint theme script is a server-neutral constant with that nonce. A style nonce anchor supports Maps' nonce discovery. HTML is private/no-store; API responses retain their existing private-response behavior.

The enforced policy blocks unapproved inline scripts, embedding, objects and external form submission, and restricts resource types/origins. X-Frame-Options DENY, nosniff, referrer policy, permissions policy and production HSTS are supplied. Styles permit inline attributes because the existing React/Recharts/Maps UI uses them. Production without Maps configuration excludes eval; when the Maps public API key is configured, the policy includes the provider's documented eval/blob exception. This is a deliberate third-party compatibility concession, not a development transport fallback. No general `unsafe-inline` script permission is enabled.

Google documents nonce discovery, strict-dynamic loading and the eval/resource allowances used by Maps. The policy includes the required Google image/connect/font/frame/worker channels. [Google Maps CSP guide](https://developers.google.com/maps/documentation/javascript/content-security-policy). Installed Next.js 16.3.4 CSP/header guidance was read before implementation. Nonce/SSR/theme/header behavior was checked against built production HTML on a private ephemeral listener without cookies or form submission. Real configured 2D/3D Maps must still be checked in the deployment browser for provider/quota and CSP violations; domain allowances may need reviewed updates as the provider changes. Do not silently broaden script policy to fix an unexplained violation.

## Validation and rollout

Reproducible commands and observed outcomes are in [RESULTS.md](RESULTS.md). The real ESP32 production toolchain compiled the actual release TLS path using isolated synthetic headers and a synthetic CA. That artifact has no field credential, field calibration or usable production endpoint and must never be flashed as a field build. Host tests preserve acquisition, GPIO, rain journaling, sequencing and offline behavior.

Before field activation: inspect the actual broker listener/authentication/ACL/firewall configuration; test credential revocation against already-connected clients; verify intended-network TLS/certificate identity and confidential traffic; review secret injection and device custody; install a release mobile build with the real HTTPS API origin; exercise account/station switches, disconnect/recovery and stale markers; validate web theme and 2D/3D Maps under the enforced CSP. Live deployment, packet-capture evidence and installed-device acceptance were not performed here. The earlier physical commissioning gates remain open.
